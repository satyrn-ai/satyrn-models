# Why `Qwen3.8-27B-py3.15` stops finishing agentic tasks: root-cause investigation

Read-only investigation, 2026-10-11, by Claude Fable 5.1 for Paul Everitt. Inputs: the 40 Pi transcripts
under `~/satyrn-runs/2026-10-10-campaign-qwen38-27b-*`, the oMLX server log, the Hub snapshot of the
tune and the base's MLX conversion, and the `satyrn-ai/satyrn-models` checkout at
`~/projects/satyrn/satyrn-model` (main `bc21146`, plus `origin/mk/*`). No model was run;
no repository was modified. Scripts used are in the scratchpad (`scan.py`, `stats.py`, `stats2.py`,
`sftdata.py`, `diffcfg.py`); every number below can be recomputed from them.

Where I say "shows" the evidence is in a file I read. Where I say "I infer" it is a mechanism that fits
the evidence but has not been tested.

---

## 1. Summary

**What the transcripts show.** The tune does not fail at tool use, and it does not fail at the coding
work. On the four repair tasks it finds and applies the right edit *faster* than base (edit on turn
3–6; base 4–11). What it cannot do is **end a turn without a tool call**. Across the 20 tune cells,
3 of 1,195 assistant turns carried no tool call (the two passes and the one `length` cut-off); base
had exactly one per cell, always the last (20 of 442). Pi ends the session only on a tool-free reply,
so every other tune cell ran to the 72-turn budget. The looping turn is always the same shape: a
complete, final-answer-style summary ("The fix is complete and verified. The bug was in …") followed
by one "closing" tool call (`pytest … | tail -3`, `git log --oneline -1`, `git status --short`,
`echo "Done"`, `echo '{"status": "success", …}'`, even `pi --task-complete 9` and
`satyrn task complete 9`). Once that happens once, the next turn is a byte-identical copy (same
thinking, same text, same call: the oMLX log shows 708 output tokens per turn, 57 turns running), at
temperature 0.6. In 217 tune turns the thinking says it should stop ("I should stop repeating the same
verification and provide a concise summary") and the model then emits a tool call anyway.

**What the training pipeline shows.** Everything the tune learned was single-turn, tool-free and
short: 5,063 SFT rows of `[user] → [assistant: <think>trace</think> explanation + exactly one
```python fence]` (100% of rows end on a code fence; 0 rows have tools, system prompts or a second
turn), rendered without `tools=` and trained at seq_len 1280 for one epoch at 2e-4 on a LoRA that
touches every attention and MLP projection of all 64 layers; before that 3 epochs of raw-document CPT
at 1e-4; after it 32 GRPO steps on 16 single-turn prompts with `beta: 0.0`. Nothing in the pipeline
shows the model a conversation that *ends after* tool use, and nothing measures one: the in-training
evals are HumanEval, a 22-row python_eval and three QA questions, all single-turn, all with
`enable_thinking=False`. Two further defects are visible in the data: (a) 991 of the 1,511
`python3.15/sft.jsonl` traces were generated by the pre-PR-19 prompt ("write why this will make a good
training example …") and open with "This is a good training example because …" — the tune's own
thinking opens with exactly that sentence in 2 of 20 cells; (b) the RL set is 16 rows.

**What is not the cause.** The serving path is identical for both models: same oMLX settings (only
model id differs), same reasoning parser, same `<|im_end|>` + `<|endoftext|>` stop set loaded from
`generation_config.json`, chat templates that render Pi's messages identically (the tune's is
Unsloth's superset of the base's), identical vocab and merges.

**Ranked hypotheses** (section 5): H1 forgetting of the episode-termination behaviour by a
tool-free, single-turn, all-layer LoRA (high confidence that this is the main effect; the specific
mechanism is inferred). H2 the SFT turn schema "prose + exactly one artifact" being transferred to
agentic turns (medium-high; explains the 97% single-call share and 408-char median text on tool-call
turns). H3 output sharpening that makes a single non-terminating turn self-perpetuating (medium; the
byte-identical repeats are the evidence, the stage responsible is not identified). H4 trace-voice
contamination from the old-prompt 3.15 data (confirmed as contamination, low as a cause of looping).
H5 CPT eroding chat behaviour (low-medium, untested). H6 GRPO collapse (low: only 32 steps).
H7 template/EOS/tokenizer defect (refuted).

**First thing to change:** make a tool-free final turn something the model is trained on and
measured on. Concretely: add multi-turn tool rows (the 16 exported base sessions plus a replay set)
rendered with `tools=` at a seq_len that keeps the final turn; drop or regenerate the 991 old-prompt
3.15 traces; add an in-training eval that scores "does the model stop after the task is done" on
held-out sessions with thinking on. Details in section 6.

Turn 7 onwards is byte-identical (thinking 169 chars, text 639 chars, same command) through turn 14;

> THINK: I've already made the fix and verified it multiple times. The test suite passes (4 passed) …
> I should stop repeating the same verification and provide a concise summary of the fix.
> TEXT: The fix is complete and verified. The bug was in `add_complaint` in `app.py`: …

shows every one of these completions as exactly `708 tokens … finish_reason=tool_calls` with the
prompt growing by 1,003 tokens per turn (37k → 51k). That is the same ~200-token message sampled 57
times at temperature 0.6, top_p 0.95, top_k 20.

The one tune cell on this task that passed (`…-020423-380721`, 8 turns) is instructive: its
intermediate texts are short (82, 44, 101 chars — agent-style, not answer-style), the turn before
the end was a `read`, and the final turn has 67 chars of thinking ("The fix is complete and verified.
Let me summarize what was done.") and no call. So termination is not impossible for the tune; it is
a probability that has dropped far enough that one "summary + closing call" turn, which then gets
copied, happens in 17 of 20 cells.

### 2.3 Other shapes of the same failure

- **Finish-seeking commands.** `selfhost-review-script` tune cells, after a correct implementation and
  commit by turn 13–15, spend the remaining ~57 turns on: `echo '{"status": "success", "message":
  "Task 9 complete …"}'` (57×), `echo "Task 9 complete: …"` (59×), `git log --oneline -1` (32–60×),
  `git status --short` (33×), `echo "Done"`, `echo "Step recording skipped"`, `satyrn task complete 9`,
  `pi --task-complete 9`, `which pi satyrn; pi --help`. The model is looking for a *tool* that ends
  the episode because it will not end it by replying.
- **Re-planning from step one.** `complaint-lifecycle` cell `…-031513-249625`: 72 turns, 72× `npm
  install express pug`. Each turn's thinking re-plans the whole job ("First, I'll set up the home page
  … install express and pug, create a package.json … write an app.js …"), executes only the first
  step, and the next turn starts over as if nothing happened. Tool results (`up to date, audited 104
  packages`) are visible in context and ignored. (It also chose Node/Express for a Python repo without
  looking; base inspected `pyproject.toml` first and used FastAPI.)
- **Thinking runaway.** Cell `agentclinic-repair-depth-3-…-214611-982374`: turn 4 produced 70,069
  chars without closing `</think>` and hit the 16,000-token cap (the only `length` stop in 40 cells).
  Cell `…-220602-351240`: 5–12k-char thinking blocks per turn, then 13 identical turns.
- **Trace voice in the thinking channel.** Two tune cells open their first thinking block with the
  SFT trace's meta-commentary:
  > This is a good training example because it shows how to build a small multi-page web app incrementally … (`complaint-lifecycle-…-031513`)
  > This is a good training example because it uses a seeded bug to teach the difference between 302/307 and 303 in Django … (`repair-depth-3-…-212140`)
  Neither "training example" nor "Django" has any source in the prompt (the app is FastAPI). No base
  cell contains this phrase.

### 2.4 What the tune does *not* do

It does not write files via heredocs more than base (0 heredoc commands in tune cells vs 3–9 in base's
lifecycle cells), does not emit malformed calls (0 parser drops in the campaign window of the oMLX
log; the 292 "Native tool parser failed" warnings in that log are all from 08:17–09:13 on 10-10,
before the campaign), and does not leak `<|im_end|>`/`<|im_start|>` into content.

## 5. Ranked hypotheses

### H1 — The LoRA forgot how to end an agentic episode (primary; confidence high that it is the main effect, medium on the exact mechanism)

**Mechanism (inferred).** Base Qwen3.8's "final turn has no tool call" behaviour is a post-training
behaviour that only exists in long, tool-bearing contexts. Fine-tuning for ~190 steps at 2e-4 (plus
~55 CPT steps at 1e-4) through a LoRA on every attention and MLP projection of every layer, on data
whose *only* way to end a turn is "prose + code fence + EOS" and whose contexts never contain a tool
schema, a `<tool_call>`, or a `<tool_response>`, moved the conditional distribution after "task done"
in a 40k-token tool context. Nothing in the loss anchored it (no replay of agentic/general data, no
KL to the base, `beta: 0.0` in GRPO).

**For.** 3/1,195 vs 20/442 tool-free turns; the finish-seeking commands (`pi --task-complete 9`,
`echo '{"status": "success"…}'`); 217 turns that say "I should stop" and don't; the tune can still
*do* the task (edits land on turns 3–6). The data has zero tool/multi-turn rows; `tools=` is never
passed; the pass cell shows termination is still reachable, i.e. the behaviour is weakened, not
deleted.

**Against / unknowns.** ~250 LoRA steps is not a lot; whether this much drift is expected from r=8
at these learning rates on a 27B is an empirical question. I cannot separate CPT, SFT and GRPO
contributions from the merged weights.

**Cheap tests.**
1. *Logit probe (offline, one forward pass per prompt, no sampling).* Take the tune cell's own context
   at the first "summary + closing call" turn (e.g. `misleading-locus-…-004118`, turn 5, rendered with
   the served template), force the assistant text up to the end of the summary, and read the next-token
   distribution: P(`<|im_end|>`) vs P(`<tool_call>`) for base and tune. Repeat on the 16 exported base
   sessions' final turns. If the tune's P(`<|im_end|>`) is an order of magnitude lower at the same
   prefix, H1 is confirmed independent of sampling.
2. *Stage ablation.* Save the adapter after each stage (`save_strategy="epoch"` or export the LoRA
   before merge) and run test 1 on CPT-only, CPT+SFT, CPT+SFT+GRPO. No stage checkpoints exist locally
   (only merged weights on the Hub), so this needs a re-run on the training machine.
3. *Replay ablation.* Re-run SFT with 10–20% of rows being multi-turn tool conversations that end with
   a tool-free turn (section 6) and nothing else changed; re-probe.

### H2 — The SFT turn schema "explanation + exactly one artifact" transfers to agentic turns (confidence medium-high as a contributor)

**Mechanism (inferred).** Every SFT completion is prose then one fenced block then stop. In an agentic
context the slot after the prose is filled by one `<tool_call>` instead of a fence. That predicts:
long answer-style prose on tool-call turns, one call per turn, and a "closing" call after the final
summary.

**For.** Median text on tool-call turns 408 chars vs 3; 66% vs 3% of tool-call turns carry >300 chars;
97% vs 73% single-call turns, 3% vs 22% multi-call; the looping turn is literally "final answer +
one call". Base's intermediate turns are tool-only (text p50 = 3 chars), the tune's never are.

**Against.** Correlational; the same observations are consistent with H1 alone.

**Cheap tests.** In the logit probe above, also measure P(first token is `<tool_call>` | empty text)
vs P(prose) at intermediate turns: the tune should prefer prose. Data-side: count fences per
completion (done: always exactly one) and consider a mix with 0- and 2-fence answers.

### H3 — Output sharpening makes one non-terminating turn self-perpetuating (confidence medium; stage unidentified)

**Mechanism.** Reproducing an ~800-char message byte-for-byte 57 times at T=0.6 needs per-token
probabilities around 0.999. In-context copying (with `preserve_thinking: true` the previous identical
`<think>` block is in context) contributes, but base never produces two identical consecutive
messages in 442 turns, including base's 46–64-turn lifecycle cells that repeat *commands* up to 10
times with varying text. The tune's thinking also has a heavier tail (70k-char runaway; 5–12k-char
blocks), the signature of a thinking channel that has lost its calibration.

**For.** 14/20 tune cells with identical consecutive turns, first at turn 5–41; runs of 33–63.
**Against.** GRPO is only ~32 steps; SFT is one epoch. Sharpening may be mostly a consequence of H1
plus copying rather than a separate cause.

**Cheap tests.** Sample n=8 continuations at T=0.6 for the same agentic prefix (one that precedes a
loop) for base and tune; report distinct-message ratio and mean per-token entropy. Then re-run one
looping cell with `preserve_thinking: false` to see whether the loop still locks in (harness-side,
diagnostic only).

### H4 — Trace-voice contamination from the pre-PR-19 `python3.15/sft.jsonl` (confirmed contamination; low as a cause of looping)

**For.** 991/1,511 traces open with dataset meta-commentary; 2/20 tune cells open their thinking with
"This is a good training example because …"; one hallucinates Django. This is direct evidence that the
`<think>` block was trained on and that the model generalises its style to new tasks.
**Against.** The two cells with the phrase are not the ones with the earliest loops, and 15 other
looping cells don't show it. It degrades thinking quality (planning "why this teaches X" instead of
"what to do next"), which plausibly feeds the re-planning-from-step-one pattern, but I have no direct
link to termination.
**Test.** Done offline (counts above). Regenerate the 3.15 traces with the PR-19 prompt and
re-measure; check `sft2.jsonl` the same way (`grep -c "training example"`).

### H5 — CPT on raw documents eroded chat/termination behaviour (confidence low-medium; untested)

3 epochs at 1e-4 over ~1.2M tokens of PEP/doc prose, packed to 4,096 with EOS only between
documents, trains "continue the document" with no chat structure; SFT afterwards re-teaches only the
single-turn chat shape. Test: the stage ablation (H1 test 2). CPT-only adapter looping in the agent
harness would implicate it.

### H6 — GRPO policy collapse (confidence low)

`beta: 0.0`, 8 epochs, but only 16 prompts × 8 generations ≈ 32 steps at 5e-6; the reward is
single-turn and `max_completion_length: 1024` with thinking on, so it rewards short thinking + a
code block. It can only sharpen (H3) and reinforce "answer = one code block" (H2); it cannot be the
sole source of a tool-context behaviour it never saw. Test: stage ablation; also log reward
distribution/entropy over the 8 epochs from MLflow.

### H7 — Template, EOS, tokenizer, or server defect (refuted, section 3)

### Not supported by evidence
- Tool-call *format* learning (0 invalid calls, parser identical).
- SFT truncation deleting EOS (~1% of rows over 1,280).
- `enable_thinking` mismatch between training and serving (both on; the system line matches).

## 6. Recommendations for the training team

Ordered by expected effect per unit of work; the first three are the ones to do before the next run.

1. **Add a termination/agentic eval before changing anything else.** An inspect-ai task over held-out
   multi-turn sessions (the exported base sessions are usable as held-out *prompts* even if not
   trained on): for each session, present the context up to the last tool result and score (a)
   whether the model's reply has no tool call when the task is done (the final turn) and (b) whether
   its next call is valid and non-repeating at intermediate turns. Run it with `enable_thinking=True`
   and at the serving sampler (T 0.6 / top_p 0.95 / top_k 20), not greedy, because the loop is a
   sampling-regime effect. Add a second, cheaper metric from the same contexts: P(`<|im_end|>`) at the
   final turn for base vs checkpoint (the logit probe), logged per stage to MLflow. Today's
   `evaluate_model` cannot see this regression.

2. **Render and train on multi-turn tool rows** (`run.py` `render_conversations_into_text_field`):
   `messages = row["prompt"] + row["completion"]`, `apply_chat_template(messages, tools=row["tools"])`,
   keep per-message `reasoning_content` instead of building it from `trace`. With Qwen3.8's template
   every `tool` message lands inside an `<|im_start|>user` block, so the existing
   `train_on_responses_only` masks tool output and trains on the model's reasoning, calls and replies
   — including the final tool-free reply, which is the behaviour to protect.

3. **Replay data, not only new data.** The 16 exported base sessions
   (`evidence/2026-10-09-qwen-py315-agentic/export/sft-agentic.jsonl`) are 5.5k–31k tokens each
   (median 16.1k). They cannot be used at seq_len 1,280; truncating would delete the final turn,
   which is the point. They *can* (a) be the held-out eval set for item 1 — this is their best use;
   (b) be trained at seq_len ≥ 32k with gradient checkpointing as a small anchor (16 rows is a
   regulariser, not a curriculum); (c) be sliced into per-turn rows (context → next assistant
   message), which keeps the final-turn examples at a few thousand tokens each and gives ~200 rows —
   but then they are no longer held out, so split by task first. They are the base model's own
   outputs (self-distillation), which is the right kind of replay for forgetting; they do not teach
   Python 3.15 and should not be expected to. For a real agentic mix you want hundreds to thousands
   of such sessions, which means generating them with base on more tasks (or using an existing open
   tool-use SFT set rendered through the same template).

4. **Fix the 3.15 traces.** Regenerate `python3.15/sft.jsonl` with the PR-19 prompt (and check
   `sft2.jsonl`), or drop the `trace` for rows whose trace matches `training example|this example`
   and render those with an empty `<think>` block. Either way, add a data gate: reject any trace
   containing "training", "dataset", "example is", "the attached".

5. **Anchor the policy.** Set `rl.beta` > 0 (e.g. 0.04) so GRPO cannot drift freely; consider a
   small KL or distillation term in SFT against the base on replayed rows; reduce LoRA scope (e.g.
   drop `out_proj`, or fewer layers) or lr (1e-4) if the ablation in item 6 shows the SFT stage
   alone causes the loss. Sixteen RL rows for 8 epochs is too few to be worth the stage until the
   RL set is larger.

6. **Save per-stage adapters** (`save_strategy="epoch"`, and push the unmerged LoRA alongside the
   merged model) so that stage ablation is a download, not a re-run.

7. **Serving note for the ledger.** The published repo ships `use_cache: false` in `config.json`
   (fixed on `mk/ornith_9b`); the MLX conversion does not care, but transformers consumers will.
