# Qwen3.8 py3.15 tune: agentic findings

2026-10-11, from Paul Everitt (measured in satyrn-evals, analysed with Claude).

**Bottom line:** the py3.15 tune still writes valid tool calls, but it has largely lost the ability to end an agentic task. Across 20 short coding tasks it delivered 2, where base Qwen3.8-27B delivered 16. It loops on "done, one more check" until the 72-turn budget runs out. Both models are served identically, so the change is in the weights. The most likely cause is the training mix, which is single-turn and tool-free.

## What we ran

We ran 40 agentic coding sessions, 20 per model, through the same harness and server settings. The only difference between the arms was the model weights.

| Item | Setting |
| --- | --- |
| Tune | `satyrn-ai/Qwen3.8-27B-py3.15`, Hub revision `f3dbc8b`, converted to MLX 8-bit |
| Base | Qwen3.8-27B, MLX 8-bit (lmstudio-community conversion) |
| Agent | Pi coding agent 1.0.2, tools `read`, `bash`, `edit`, `write` |
| Server | oMLX on an Apple M5 Max, one session at a time |
| Sampling | temperature 0.6, top_p 0.95, top_k 20, thinking on, 16,000-token reply cap |
| Budget per session | 48,000 output tokens or 72 turns, whichever comes first |
| Tasks | 5 short tasks, 4 sessions each per model: three seeded bug repairs in a small FastAPI app, a feature build in the same app, and one plan task in a Python repo |
| Grading | hidden pytest suites the model never sees |

## What we saw

**Tool-call formatting is fine.**
- No tool calls were left as text, in either JSON or Qwen's XML form.
- No call was invalid.
- One tune reply was cut off at the 16,000-token cap; base had none (1/20 vs 0/20).

**Finishing is not.** "Delivered" means a passing fix by the end of the session:

| Task | Base: delivered | Tune: delivered | Base: median turns | Tune: median turns |
| --- | --- | --- | --- | --- |
| Plan task (review script) | 4 of 4 | 0 of 4 | 21.5 | 72 |
| Repair: depth-2 | 4 of 4 | 1 of 4 | 13 | 72 |
| Repair: depth-3 | 4 of 4 | 0 of 4 | 11.5 | 48.5 |
| Repair: misleading locus | 4 of 4 | 1 of 4 | 8 | 72 |
| Feature build (complaint lifecycle) | 0 of 4 | 0 of 4 | 57.5 | 72 |
| **All** | **16 of 20** | **2 of 20** | | |

- **The tune ran out the budget.** It hit the 72-turn limit in 17 of 20 sessions, and one more ended with no patch.
- **Base's feature-build sessions don't count against it.** They finished on their own, but the grader rejected them for touching a file outside the allowed paths.
- **How far to trust it:** the per-task rows are indicative only. The 16 vs 2 total is the robust number.

## How it fails

The tune does the work, often faster than base, and then cannot end its turn without calling a tool. Pi ends a session only on a reply with no tool call:
- **Tune:** 3 of 1,195 turns had no tool call: the two passes and one cut-off reply.
- **Base:** one per session, always the last turn (20 of 442).

The looping turn is always a final-answer summary plus one "closing" tool call:

> **Thinking:** I've already made the fix and verified it multiple times. The test suite passes (4 passed) … I should stop repeating the same verification and provide a concise summary of the fix.
>
> **Text:** The fix is complete and verified. The bug was in `add_complaint` in `app.py`: …
>
> **Tool call:** `uv run python -m pytest tests/ -q 2>&1 | tail -3`

Once that turn appears, the following turns are byte-identical copies, at temperature 0.6. In one session the same 708-token message was produced 57 times. In 217 tune turns the thinking says the model should stop, and then it calls a tool anyway. The model also goes looking for a tool that will end the episode, with calls such as:
- `echo '{"status": "success", …}'` (57 times in one session)
- `git log --oneline -1`
- `echo "Done"`
- `satyrn task complete 9`
- `pi --task-complete 9`

| Per session (median) | Base | Tune |
| --- | --- | --- |
| First edit or write, repair tasks | turn 4–11 | turn 3–6 |
| Turns | 14 | 72 |
| `bash` calls | 14 | 68 |
| Tool calls repeating an earlier identical call (all sessions) | 2% | 76% |
| Longest unbroken run of `bash` calls | 7 | 66 |
| Text on a tool-call turn (characters) | 3 | 408 |
| Turns with more than one tool call (all sessions) | 22% | 3% |
| Sessions with byte-identical consecutive turns | 0 of 20 | 14 of 20 |
| Wall time | 12.9 min | 27 min |

Output per turn is the same for both models, about 245 tokens. The tune takes longer only because it never stops.

Two less frequent patterns:
- **Re-planning from scratch.** In one feature-build session, the tune re-planned the whole job every turn and ran `npm install express pug` 72 times, ignoring the tool output. It chose Node for a Python repo without looking; base read `pyproject.toml` first.
- **Training-data voice in its thinking.** Two tune sessions open their thinking with "This is a good training example because …". One of them also mentions Django, which appears nowhere in the task. No base session contains that phrase.

## Why: likely causes in the pipeline

The most likely cause: the LoRA wore away base's habit of ending an agentic episode, because nothing in training ever showed one or measured one.

**The serving path is ruled out.** It's the same for both models:
- the same oMLX settings;
- the same stop tokens (`<|im_end|>`, `<|endoftext|>`);
- an identical vocabulary;
- chat templates that render Pi's messages byte-identically. The tune's Unsloth template is a superset of Qwen's.

Pipeline facts, at `bc21146`:
- **SFT:** 5,063 rows, every one single-turn and tool-free.
  - Every completion is prose plus exactly one fenced code block.
  - No row has a system prompt, a tool schema or a second turn.
  - `render_conversations_into_text_field` (`run.py` L68–81) uses only `completion[0]`, with no `tools=`.
  - Training: seq_len 1280, 1 epoch at lr 2e-4, LoRA r=8 on every attention and MLP projection of all 64 layers.
- **CPT:** about 1.2M tokens of PEP and doc prose, 3 epochs at 1e-4.
- **GRPO:** 16 single-turn prompts, about 32 steps, `beta: 0.0`, max completion 1,024.
- **In-training evals:** HumanEval, `python_eval` and a 3-question QA. All single-turn, greedy, `enable_thinking=False`. None of them can see this regression.

| Rank | Hypothesis | Evidence | Confidence |
| --- | --- | --- | --- |
| 1 | **Forgetting of episode termination.** A tool-free, single-turn LoRA over all layers, with no replay and no KL anchor, moved what the model does after "task done" in a long tool context. | 3 of 1,195 tool-free turns vs 20 of 442; finish-seeking commands; 217 "I should stop" turns that call a tool anyway. The task work itself is intact. | High that this is the main effect; the mechanism is inferred |
| 2 | **The SFT turn shape transfers.** "Prose + exactly one artifact" becomes "prose + exactly one tool call", so even the final summary gets a closing call. | Median 408 characters of text on tool-call turns vs 3; 97% vs 73% single-call turns. The loop turn is "answer + one call". | Medium-high, as a contributor |
| 3 | **Output sharpening.** One non-terminating turn then copies itself. | 14 of 20 sessions with byte-identical consecutive turns at temperature 0.6 (runs of 33–63). Base never repeats a message. A 70,000-character runaway thinking block. | Medium; the responsible stage is not identified |
| 4 | **Trace-voice contamination.** 991 of 1,511 traces in `python3.15/sft.jsonl` came from the pre-PR-19 prompt and open "This is a good training example because …". | Two tune sessions open their thinking with exactly that sentence. PR #19 fixed the prompt, but the 3.15 file was never regenerated. | Confirmed as contamination; low as a cause of looping |
| 5 | **CPT eroding chat behaviour.** | None direct. | Low-medium, untested |
| 6 | **GRPO collapse.** | About 32 steps; it can sharpen (3) and reinforce (2), but can't cause them alone. | Low |
| 7 | **Template, EOS or tokenizer defect.** | Checked and refuted. | Ruled out |

Not checked: the exact config revision and dataset mix of the published run (MLflow has them), and whether `sft2.jsonl` was in the mix. It wasn't in the local LFS copy we read.

## What to change first

Make a tool-free final turn something the model is trained on and measured on. These are in order of expected effect per unit of work. The first three come before the next run.

1. **Add an agentic termination eval.** Without it, no fix can be checked.
   - Use an inspect-ai task over held-out multi-turn sessions. Give the model the context up to the last tool result.
   - Score (a) whether the reply has no tool call when the task is done, and (b) whether intermediate calls are valid and non-repeating.
   - Run with `enable_thinking=True` at the serving sampler (temperature 0.6, top_p 0.95, top_k 20), not greedy: the loop only shows up when sampling.
   - As a cheap companion, log the probability of the end-of-turn token at the final turn, for base and for each checkpoint, per stage.
2. **Render and train multi-turn tool rows.**
   - In `render_conversations_into_text_field`, use `messages = row["prompt"] + row["completion"]` and `apply_chat_template(messages, tools=row["tools"])`.
   - Keep each assistant message's own `reasoning_content`, rather than building it from `trace`.
   - Qwen3.8's template puts every `tool` message inside a user block, so the existing `train_on_responses_only` already masks tool output. The loss lands on reasoning, calls and the final tool-free reply.
3. **Replay, not only new data.** Mix in multi-turn agentic sessions that end with a tool-free turn, ideally the base model's own (self-distillation). A real mix needs hundreds to thousands of sessions. Generate them with base on more tasks, or render an open tool-use SFT set through the same template.
4. **Fix the 3.15 traces.**
   - Regenerate `python3.15/sft.jsonl` with the PR-19 prompt, and check `sft2.jsonl`.
   - Or drop the trace on rows matching `training example|this example` and render an empty think block.
   - Add a data gate that rejects traces containing "training", "dataset", "example is" or "the attached".
5. **Anchor the policy.**
   - Set `rl.beta` above 0, for example 0.04.
   - Consider a KL or distillation term against base on replayed rows.
   - If a stage ablation shows SFT alone causes it, lower the SFT learning rate (for example 1e-4) or the LoRA scope.
   - Sixteen RL prompts for 8 epochs is too few until the RL set grows.
6. **Save per-stage adapters.** Push the unmerged LoRA alongside the merged model, so a stage ablation is a download, not a re-run.

One small thing: the published `config.json` ships `use_cache: false`. It's fixed on `mk/ornith_9b`, not on main.

## The sessions in `datasets/agentic/`

`qwen3.8-27b-base-sessions.jsonl` holds 16 base Qwen3.8-27B sessions that passed the hidden tests: plan task 4, depth-2 4, depth-3 4, misleading locus 4.

**Row format.** The rows keep this repo's prompt/completion shape and all eight keys:
- `prompt` is `[system, user]`: Pi's system prompt, then the task.
- `completion` is the whole session, in order:
  - assistant messages with `reasoning_content`, `content` and, when the model called a tool, `tool_calls` (arguments as objects);
  - `tool` messages with the tool output.
- `tools` has the four tool schemas, in OpenAI function form.
- `source` has provenance: model, record, task tree hash, verdict, rendered token count and turns.

Every row renders through the served chat template without error, and tool output sits inside the masked user spans. Paths and usernames are redacted. The plan-task sessions contain source code from the satyrn-evals repository's task snapshot.

**Length.** Rendered rows are 5,537 / 16,100 / 30,872 tokens (min / median / max). None fits seq_len 1280. Truncating would delete the final tool-free turn, which is the thing to teach. Ways to use them:

1. **As the held-out eval for recommendation 1.** This is the best use.
2. **As a small anchor at seq_len 32k or more,** with gradient checkpointing. Sixteen rows regularise; they don't teach.
3. **Sliced into per-turn rows** (context, then the next assistant message): about 200 rows. Split by task first, so some stay held out.

They are base's own outputs, the right kind of replay for forgetting. They don't teach Python 3.15.

## Cheap tests to confirm the cause

| Test | How | Confirms | Cost |
| --- | --- | --- | --- |
| Logit probe | At a tune session's first "summary + closing call" turn, force the assistant text through the end of the summary and compare the probability of the end-of-turn token with that of a tool-call opening, for base and tune. Repeat at the 16 base sessions' final turns. | H1: the tune's end-of-turn probability is an order of magnitude lower at the same prefix | One forward pass per prompt |
| Turn-shape probe | Same contexts, intermediate turns: probability that the first token opens a tool call vs prose | H2 | Same pass |
| Stage ablation | Logit probe on CPT-only, CPT+SFT and CPT+SFT+GRPO adapters | Which stage causes it (H1, H5, H6) | A re-run with per-stage adapters saved |
| Sampling distinctness | 8 continuations at temperature 0.6 from a prefix just before a loop, base vs tune | H3: the tune's continuations collapse to one message | 16 generations |
| Trace grep | `grep -c "training example"` on each SFT file | H4: done for the local files (991 of 1,511 in 3.15); `sft2.jsonl` unchecked | Seconds |
| Replay ablation | Re-run SFT with 10–20% multi-turn tool rows that end tool-free, nothing else changed; re-probe | That replay fixes it | One SFT run |

## Caveats

- **Scope:** five short tasks, 4 sessions per task per model, one budget, one machine. The 16 vs 2 gap is large enough to trust; the per-task rows are indicative.
- **Planned test vs observation:** the test planned in advance was tool-call format failures, which came out even. The delivery and looping findings were observed. That's fine for diagnosis, but a formal claim would need its own run.
- **Repaired tool calls:** calls the server's parser repaired count as working. Raw completions were not captured.
- **Thinking kept in context:** Pi keeps every earlier thinking block in context (`preserve_thinking: true`). That's the same for both models, but it amplifies a loop once one starts.
- **Open questions:**
  - Which config revision and dataset mix produced the published model?
  - Was `sft2.jsonl` in it?
  - Do any intermediate-stage adapters exist?
