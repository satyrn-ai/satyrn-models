# Cycle 3.1: Execution layer and structured outcome — design

## Purpose

Implement Phase 3's execution layer: run a candidate program and its checks in
an isolated executor, return a **structured outcome** (never a blob of text),
and parse a JSON verdict by scanning stdout **backwards**. Uses the imported
`satyrn.dataset` gVisor sandbox (decision 1) for the real run, with an
injectable subprocess executor so the outcome logic is testable without Docker.

## Context

- Roadmap M1, Phase 3 (first cycle). BRIEF Phase 3 (execution layer) + §2.2.
- Prior: Cycle 2.2 merged (57 tasks, 6 cells). Cycle 2.1's spec defined the
  negative_control qualification rule (used in Cycle 3.2).
- Convergence: decision 4 (import `satyrn.dataset`) becomes real here — this is
  the cycle that adds `satyrn-corpus-builder` as a path dependency.

## Rulings (recommendations)

1. **Executor is injectable.** `run_candidate(code, checks, *, timeout=10, executor=None)`. The default executor runs the program through
   `satyrn.dataset.utils.sandbox.Sandbox` (gVisor Docker). Tests inject a
   subprocess-based executor so the Outcome/verdict logic is testable without
   Docker. The real gate run (Cycle 3.2) uses Docker.
2. **Verdict framing.** The harness wraps the candidate + checks into a program
   whose **last stdout line** is a single JSON object — the verdict. Parsing
   scans stdout backwards for the last parseable JSON object, so a candidate
   that `print()`s arbitrary mid-run output (e.g. `{"x": 1}`) cannot corrupt
   the verdict (this is the measured parsing bug from BRIEF §4).
3. **Dependency wiring.** Add `satyrn-corpus-builder` as a path dependency of
   the spike (non-editable, `path = "../../corpus_builder"`), so
   `import satyrn.dataset.utils.sandbox` resolves. This pulls `corpus_builder`'s
   transitive deps (`sphinx`, `openai`, `rich`, `tqdm`, `jsonschema`,
   `python-dotenv`) into the spike venv — accepted per decision 4.

## Components

### `types.py` additions (BRIEF Phase 3)

```python
@dataclass(frozen=True, kw_only=True)
class Accepted:
    observations: dict

@dataclass(frozen=True, kw_only=True)
class Rejection:
    stage: str   # "syntax" | "import_policy" | "runtime" | "semantic_check"
    detail: str

@dataclass(frozen=True, kw_only=True)
class InfrastructureFailure:
    detail: str  # timeout, harness crash, unparseable verdict

Outcome = Accepted | Rejection | InfrastructureFailure
```

### `gate.py` (execution layer, this cycle)

- `run_candidate(code: str, checks: tuple[Check, ...], *, timeout: int = 10, executor=None) -> Outcome`:
  1. Build a wrapper program: run `code` in a namespace; for each `Check`,
     evaluate it (`expected_stdout` compares captured stdout; `expected_value`
     compares a returned value; `uses_feature` verifies the code's AST contains
     the required node/module); emit one JSON verdict line as the last stdout
     line.
  2. Run the wrapper via the executor; on timeout/harness crash → `InfrastructureFailure`.
  3. Scan the captured stdout backwards for the last parseable JSON object →
     the verdict. Unparseable → `InfrastructureFailure`.
  4. Decode the verdict into `Accepted(observations)` or
     `Rejection(stage, detail)`.
- `_subprocess_executor(program: str, timeout: int) -> str` — the Docker-free
  executor used by tests (and a documented fallback).

### Dependency wiring

- `pyproject.toml`: `dependencies` gains
  `"satyrn-corpus-builder @ file://../../corpus_builder"` (or uv `path` table);
  `uv lock` + `uv sync` re-resolve.

## Testing

1. A known-good program whose check passes → `Accepted`.
2. A program failing a `uses_feature` check → `Rejection(stage="semantic_check")`.
3. A program whose candidate `print()`s `{"x": 1}` mid-run still yields the
   correct verdict (backwards parse).
4. A program with unparseable final output → `InfrastructureFailure`.
5. A timeout → `InfrastructureFailure`.
6. A syntax error → `Rejection(stage="syntax")`.
7. `_subprocess_executor` runs a trivial program and returns its stdout.

## Out of scope

- `qualify`, degenerate families, negative_control special-casing — Cycle 3.2.
- Anything that mutates `tasks/built.jsonl` or `reports/`.

## Decomposition

Cycle 3.1 = one feature cycle (this). Cycle 3.2 is the gate on top.
