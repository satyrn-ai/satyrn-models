# Cycle 9.1: Michal-format delivery — design

## Purpose

Convert the frozen corpus (`corpus-sft/`, 589 rows) into the exact row schema
Michal ships in `datasets/python3.14/sft.jsonl`, so he can consume it directly:
a user-only `prompt` holding a generated natural question, a `completion` of
explanation prose + the mined code in a fenced block, and a full first-person
reasoning `trace`. This is Roadmap **M4 "Delivery"** (Phase 9). The BRIEF
governs Phases 0–8; this document is Phase 9's spec.

## Context

- Roadmap M4, Phase 9. BRIEF Phases 0–8 are unchanged; Phase 9 is new.
- Michal's schema read directly from `datasets/python3.14/sft.jsonl` on `main`
  (1537 rows; 8 keys; user-only `prompt`; prose+fence `completion`; reasoning
  `trace`). His generation intent lives in
  `corpus_builder/src/satyrn/dataset/sft.py` (`generate_code_block`'s trace
  instruction and `generate_conversation`).
- Prior: Phase 5 (`render` + `freeze`) produced `corpus-sft/{train,valid}.jsonl`
  with the converged schema — system prompt as first `prompt` entry, code-only
  fenced `completion`, one-line `trace`.

## Rulings (recommendations)

1. **Approach: a self-contained `deliver` command in the spike.** New
   `deliver.py` + `deliver` CLI command reusing `satyrn.dataset.llm`
   (`get_llm`, `Context`), not Michal's functions. His `generate_conversation`
   is coupled to `Idea`/doc-file/`Sandbox`, and his trace instruction is
   bundled inside `generate_code_block` (LLM *code*-gen we deliberately skip),
   so re-implementing the two prompts as constants — each with a pointer
   comment to `sft.py` — is cleaner and unit-testable. (Upstreaming the step
   into `corpus_builder` is a later, optional M3-adjacent follow-up.)
2. **Target schema — exactly Michal's 8 keys.** Per row:
   - `prompt` = `[{"role": "user", "content": <generated natural question>}]`
   - `completion` = `[{"role": "assistant", "content": "<explanation>\n\n```python\n<code>\n```"}]`
   - `idea`, `code`, `expected_output`, `filename`, `python_version` carried
     over verbatim from the frozen row.
   - `trace` = generated reasoning chain.
   - Dropped: the row-level system message, `_line`, `semantic_id`.
3. **System prompt distinction.** Keep Michal's *generation-time*
   `SYSTEM_PROMPT` ("You are an expert Python instructor writing teaching
   material for the newest Python release.") for both LLM calls. Drop the
   *row-level* system message from `prompt` — his shipped rows carry none
   (`prompt` is user-only). This supersedes convergence-amendment 2 for the
   delivered rows; the train/eval-alignment concern becomes a note in the PR
   conversation, not a field in the data.
4. **Two generation steps, in his order, both `thinking=True`.** Model
   `deepseek-v4-flash` (same as his `get_llm("deepseek", "deepseek-v4-flash")`).
   - **Step 1 (trace), plain text**, mirrors `generate_code_block`'s trace
     instruction: "Write the reasoning that leads to this code, in first person
     and present tense, as you would think it through before writing it: what
     the task requires, which Python 3.14 feature applies and how it behaves,
     how the code uses it, and step by step what each statement prints as it
     runs. Write as though you thought of the task yourself: do not mention the
     attached document, the idea, training, datasets, or examples, and do not
     address the reader. Keep it concise: at most 1200 characters." Fed: `idea`
     + `code` + `expected_output`.
   - **Step 2 (question + explanation), JSON schema `{"prompt", "explanation"}`**,
     mirrors `generate_conversation`, with one addition — the question is
     anchored to the idea: "The question must match the 'Example idea' below;
     do not invent a different domain or topic for it." Fed: `idea` + `code` +
     the trace from step 1.
5. **Completion assembly (exact):** `f"{explanation}\n\n```python\n{code}\n```"`,
   matching `sft.py`'s `generate_conversation`.
6. **No source-file context.** The whole-file source attachment was dropped
   after the first live run: it made the LLM infer the *file's* domain (SQL,
   HTML, DOM) and write questions that contradicted the generic `idea`. The
   mined `code` field is already the self-contained enclosing unit (it passed
   the execution gate), so generation uses `idea` + `code` + `expected_output`
   only. Per-row source lookup and `--checkouts-dir` are removed; the manifest
   still records the `sources.toml` pins as provenance.
7. **Outputs + resumability.** `delivery/sft.jsonl` (single combined file,
   589 rows, Michal's schema) + `delivery/manifest.json`: input fingerprints
   (corpus-sft, gated.jsonl), the `sources.toml` pins, output row count, the
   train/valid split mapping by `semantic_id`, provider/model/effort, a
   generation timestamp, and a `mock`/incomplete note. `deliver` is resumable:
   each completed row is checkpointed to `delivery/_checkpoint.jsonl` keyed by
   `semantic_id`, failed rows are logged and left un-checkpointed, and a later
   run (`--workers` for parallelism, `--fresh` to discard the checkpoint) skips
   completed rows and retries the rest. Output prose is LLM-generated and
   non-deterministic; the manifest fingerprints the deterministic *inputs*.
8. **Mock LLM.** `deliver` is unit-testable without a key: the mock keys off
   `context.expect_json` — plain text for the trace step (fixed reasoning
   string), `{"prompt": …, "explanation": …}` for the conversation step.
9. **No `judge_conversation` in v1.** Our code is already verified
   deterministic; the judge would only gate prose. `--preview` (mirroring his
   `sft.py --preview`) plus a manual review of a few rows suffices. The judge
   can be mirrored later if quality warrants.

## Components

- `src/satyrn/tstrings/deliver.py` — the `deliver` CLI command:
  - options: `-i/--input-dir` (default `corpus-sft`),
    `-o/--output-dir` (default `delivery`), `--llm` (default `deepseek`),
    `--model` (default `deepseek-v4-flash`), `--mock-llm`, `--preview`,
    `--checkouts-dir` (default `.cache/sources`).
  - functions: `generate_trace(...)`, `generate_conversation(...)`,
    `assemble(...)`, `write_manifest(...)`; registers on the CLI group beside
    `freeze`.
- A mock LLM that returns a string when `context.expect_json` is false and the
  conversation dict when true (extending or replacing `_MockLLM` in `cli.py`).

## Testing

1. Trace step returns a string; conversation step returns the JSON dict; both
   exercised with the mock LLM.
2. `assemble` produces the exact completion string
   (`explanation + "\n\n```python\n" + code + "\n```"`) and the 8-key row —
   no system message, no `_line`, no `semantic_id`.
3. `prompt` is user-only; `completion` is assistant-only.
4. The mock keys correctly on `expect_json` (false → string, true → dict).
5. Source context: a planted source file's content reaches the `Context` for
   the right `source_id`, and the re-join fails loudly on a missing gated task.
6. `write_manifest` records the split mapping (a `semantic_id` in train maps to
   train), the input fingerprints, and the `mock` note under `--mock-llm`.
7. CLI end-to-end (mock): `deliver` writes `delivery/sft.jsonl` with 589 rows
   and `delivery/manifest.json`.

## Out of scope

- `judge_conversation` quality gate (v1 manual review only).
- Upstreaming the step into `corpus_builder` (future PR, M3-adjacent).
- Regenerating `idea`/`code`/`expected_output` — those stay deterministic.
